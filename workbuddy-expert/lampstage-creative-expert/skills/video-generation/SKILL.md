# Video generation

For 婴儿服装、童装、宝宝穿衣、换宝宝、换妈妈 or 床单换色, read [infant-clothing.md](references/infant-clothing.md) first. Use the [review record](references/replication-review-template.md) for the brief, attempts and final review.

1. Collect the source video, product image, approved character/scene images, required changes, preserved motion/audio and budget authorization. Reuse confirmed facts. List essential actions as before → contact/operation → after. The source must be 9:16 and 4–30 seconds. Automatic 4–5 second windows are model-sized slices; they are not semantic action windows.
2. Check `health`, `capabilities` and tool schemas. Use `direct_references` for new replication jobs. Require the `video.replicate` entry in the `capabilities` array, with `modes.direct_references` and `status: available` before creating or preparing. If absent, explain that a supporting server deployment is needed and stop. Do not silently switch to legacy mode. The mode accepts exactly three image inputs: `product_asset_id` becomes Picture 1; exactly two ordered `reference_assets` become Pictures 2 and 3. Each has a distinct `asset_id`, `role` (`character`, `scene`, or `product_detail`) and a specific nonempty `label` up to 80 characters. For a baby and mother, label both explicitly. A separate scene image must occupy one of those two slots or already appear in a confirmed reference; otherwise the source video supplies scene context. Never discard, combine or duplicate assets to fit the slots. An essential fourth independent image is a capability gap.
3. Create with `generation_mode: "direct_references"`, source/product IDs, the ordered references, and optional title, instructions and preserve_audio. Inspect the returned `generation_mode` and actual `reference_assets` order. `prepare_video_job` snapshots those references and source windows; it does not generate opening/ending frames or use image generation calls in this mode. Do not prepare first/last frames as a prerequisite. Image preparation for another need requires an explicit user choice. Legacy jobs keep their existing preparation behavior and may incur image-generation cost.
4. Query `get_job` after preparation. Show all three reference URLs, labels/roles and hashes, `references_ready`, `source_duration`, and the source windows. Check each image against the brief and source motion. Show the current coin quote and obtain explicit budget consent before `render_video_job` with `max_coins`. **Pass the `review_token` returned by that same `get_job` call**: it binds the job, mode, reference snapshot, motion windows, pending segments and the shown quote. If anything changed since you showed it (price, references, windows or segment set), the server refuses with `409 review_changed` and you must show the review again instead of retrying. Never fetch a fresh token right before submitting in order to bypass this. Existing specific authorization may satisfy the budget part. A requested cap is not a guaranteed provider cost limit. Do not render if references are missing, out of order, or an essential action is cut; current automatic segmentation cannot promise semantic windows.
5. Poll the same job ID with bounded backoff. Timeout means unknown; query the existing job before any retry. Record paid and unused attempts and unsettled costs. After completion, inspect the encoded video for identities, product, motion/order, contact, joins, scene and audio. Mark checks you could not perform as pending. A completed job is a preview awaiting review, not proof of acceptance.

Keep credentials secret. Do not publish without authorization or claim unavailable controls such as independent fourth reference, custom timeline, mask recoloring, selected-segment rendering or narration mixing.
