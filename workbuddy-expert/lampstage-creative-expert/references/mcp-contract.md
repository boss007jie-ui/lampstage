# Lampstage API connector contract · 0.10.1

Remote tools (27): `health`, `capabilities`, `upload_asset`, `create_image_job`, `create_video_job`, `prepare_video_job`, `render_video_job`, `review_video_segments`, `assemble_video_job`, `reconcile_video_job`, `get_job`, `download_output`, `get_account_usage`, `list_video_jobs`, `cancel_video_job`, `close_video_job`, `get_video_delivery`, `submit_video_feedback`, `list_video_templates`, `get_video_template`, `update_video_template`, `list_characters`, `get_character`, `save_character`, `save_character_version`, `update_character`, and `list_character_assets`. The bundled stdio bridge adds `upload_local_asset` (28 tools total).

The bridge uses the user's `LAMPSTAGE_API_KEY` to call `/api/v1`. Provider credentials stay server-side. The bundled stdio bridge also exposes `upload_local_asset {file_path,kind}` for an explicitly supplied absolute local path. It validates regular JPEG/PNG/WebP images up to 5 MiB and MP4/MOV/WebM videos up to 150 MiB, then sends authenticated multipart to `/assets` or `/video-assets`. The remote HTTP MCP endpoint cannot read client files and still exposes URL-based `upload_asset` for public `http(s)` sources. Do not use a temporary public host as a hidden workaround.

## Image creation

Check live `image.generate` with `status: available`, `inputs.reference_assets.schema_version:1`, `ordered:true`, declared limits/models and `provider_validation` before using ordered references. Read the [image workflow](../skills/image-generation/references/multi-reference-images.md). The local and remote `create_image_job` schemas require `custom_prompt` (1–12000 characters) and `image_count` (integer1–4 outputs), with exactly one of `asset_id` or `reference_assets`. Reference count is independent of output count. Four separate mother/baby/product/scene images can request one complete scene; no pre-composed collage is required.

`reference_assets` is the complete ordered list of1–6 `{asset_id,role,label,character_version_id?,image_index?}` items. Roles are `character`, `product`, `product_detail`, `scene`, `start_state`, `end_state`; label is nonempty ≤80 with no C0/DEL, and IDs use `[A-Za-z0-9_-]{1,128}`. No duplicate IDs, unknown item fields, silent dropping/reordering or merging with `asset_id`/`uploaded_asset_id`. Character version and integer0–5 image index must be paired, only on role character; the actual owned asset must match that fixed version/index. Unlike video-template replacement, null is invalid here; an ordinary unbound image omits both fields. Server ownership/content/archive checks remain authoritative and also reject duplicate exact image content.

Optional fields: `image_model: "nano_banana_21"|"image_25"` (default nano), `platform_style: "domestic_ecommerce"|"brand_site"`, and `aspect_ratio: "1_1"`. Both models have an application reference limit of6, not a verified upstream maximum. Nano uses ordered image parts; the image2.5 gateway alias uses the single-image or multiple-image form as appropriate. OpenLux four/six-image acceptance and generation quality remain unverified by live paid tests. Do not auto-switch models or probe with paid jobs.

MCP does not expose `scene_kind`, `template_id` or `recommended_prompt_en`. The underlying REST array route accepts only omitted/custom scene_kind and rejects template/recommended fields. Single-asset MCP calls map `asset_id` to the REST `uploaded_asset_id`; array calls never add that alias. Both MCP paths require an explicit prompt and output count in the schema and at runtime. Old single-asset REST/profile defaults remain server-side compatibility only; do not bypass tool requirements or inherit an unspecified paid output count.

`create_image_job` calls `POST /image-jobs` once and starts paid image work. Save its returned `job_id` and read `get_job` (`GET /jobs/:id`). New reference jobs expose `reference_schema_version:1`, `reference_count`, ordered `reference_assets` with SHA256 and selected character bindings, and `image_count`. These fields document inputs; they do not prove generated quality. They do not include internal storage locations or image bytes. Compare actual completed outputs before video use or publication.

Unknown transport or malformed success responses return `api_request_outcome_unknown`, `retryable:false` in the bridge. Query a known job ID; without an ID use an actually supported account image-history interface, or report unresolved status. There is no image-list tool in this release; `list_video_jobs` cannot reconcile an image create. Never use its empty result to repeat the image POST. Preserve safe error codes without arbitrary diagnostics, URLs or credentials.

## Video creation

For new video work, check the `video.replicate` capability entry: `status: available` and `modes.six_references: true`. `create_video_job` takes `source_asset_id`, `generation_mode: "six_references"`, an ordered `reference_assets` array of 1–6 `{asset_id, role, label}` entries, and a required `segment_plan`. Each effective segment reference list must have exactly one `start_state` in its first slot; a per-segment override is a complete list subject to the same rule. Roles are `product`, `character`, `scene`, `product_detail`, `start_state`, `end_state`. `product_asset_id` is optional and never forces a product into the first reference slot. Existing job reads preserve recorded order. Global `instructions` state appearance and preservation rules, while segment `instructions` describe only local actions.

`segment_plan` has 1–8 entries: `{start, source_duration, duration, instructions, before_state, after_state, reference_assets?, start_from_segment?}`. Windows cover the source in order with no gaps. `duration` is 4, 5, 6 or 8 seconds; the larger of `source_duration/duration` and `duration/source_duration` must be at most 1.15. Segment references, if supplied, replace the common list as a complete ordered list. `start_from_segment` must point to an earlier segment and its accepted real tail replaces the first `start_state` image without reordering; the dependent segment cannot render until review accepts that tail. State references are ordinary images, not dedicated endpoint controls. Preparation snapshots/normalizes existing references and source windows, and does not create multi-reference state images.

Preflight limits: reference labels ≤80 characters, segment instructions ≤1600, before/after states ≤400 each, title ≤80 and global instructions ≤2000 (JavaScript string length). Labels and segment text must be nonempty and contain no C0/DEL control characters, including newlines and tabs. Do not silently truncate creative requirements. Asset IDs use 1–128 ASCII letters/digits/underscore/hyphen. The local bridge rejects invalid payloads before network work and forwards only allowlisted `invalid_video_references` messages; unknown diagnostics remain hidden. Input validation does not prove account ownership or server readiness. Follow [production workflow](../skills/video-generation/references/production-workflow.md) for bounded 30–60-second polling, full playback checks, signed URL handling and full-plus-segment delivery.

`get_job` returns reviewable references, quote, `review_token`, `ready_segment_indices`, and later `candidate_review_token` plus each segment's candidate `candidate_sha256`, `tail_url`, `tail_sha256`, and `accepted` state. After reviewing the plan and quote with the user, `render_video_job` sends `{job_id, max_coins, review_token}` for currently ready independent segments. The server limits RunningHub requests to three across the account. Unknown receipt means query the same job; never repeat a paid submission to guess. A requested `max_coins` is not a guaranteed upstream ceiling when pricing is unknown.

Each segment in `get_job` may contain `candidate_timing`: `status` is `compatible|incompatible|unknown`; `reason` is `compatible|actual_duration_unknown|invalid_source_window|invalid_trim|duration_out_of_range`. `source_duration/requested_duration/actual_duration/trim_start/kept_duration/delivery_duration/retime_ratio` are numbers or null, alongside `max_retime_ratio:1.15`, `allowed_kept_duration:{min,max}|null`, and `visual_review_required:true`. Official assembly can hold the final frame for at most one 30 fps frame (1/30 second) to meet delivery frame count; explicit reviewed trim and the 15% retime limit still apply. This free calculation does not establish visual quality. A 400 `invalid_candidate_review` may expose safe `reason`, optional `segment_index` and the timing object. Valid reasons are `invalid_decisions|invalid_segment|candidate_changed|candidate_incomplete|invalid_trim|actual_duration_unknown|duration_incompatible|invalid_source_window|retry_trim_conflict|retry_reason_required|dependent_result_exists|invalid_action`. The local bridge accepts only known enum values and bounded numbers, never arbitrary server diagnostics.

Play candidate videos before calling `review_video_segments` with `{job_id, candidate_review_token, decisions:[{segment_index,candidate_sha256,action:"accept"|"retry",reason?,trim_start?}]}`. `trim_start` is an optional nonnegative leading trim on an accepted candidate, used only after checking the actual action and resulting kept duration; it is not allowed on retry. Terminal failed segments have `candidate_sha256: "failed"` and can only be retried with a specific reason. Retrying only the rejected segment may incur new cost. After all candidates are accepted, `assemble_video_job` takes `{job_id,candidate_review_token}`. If a job enters `attention` with an unknown existing submission, `reconcile_video_job` takes `{job_id}` and checks its recorded receipt; it must not create a fresh generation. Play the final encoded video and verify its actual dimensions, duration, and audio. Existing jobs keep their recorded provider route and review-token requirements; no automatic fallback or conversion is allowed.

## Lifecycle version 1

Plan, edit and check input locally before explicit submission creates one video task. Persist its ID outside this package and reuse it for the existing create→prepare→review→render flow. This release provides neither remote draft editing nor create-idempotency keys. If the create response is lost, stop automatic POSTs and use list/get recovery; never create a test task or assume a title uniquely identifies the result.

The `video.replicate` capability entry advertises:

```json
{"lifecycle":{"version":1,"draft_limit":10,"active_limit":10,"draft_ttl_seconds":86400,"cancellation":"never_started_drafts","closing":"explicitly_abandoned_stopped_review_or_attention","terminal_statuses":["completed","failed","cancelled"]}}
```

Its endpoints include `account_usage: "/api/v1/account/usage"`, `video_cancel: "/api/v1/video-jobs/:id/cancel"`, `video_close: "/api/v1/video-jobs/:id/close"`, and the existing `video_jobs` path supports GET. Live remote `tools/list` exposing the corresponding lifecycle tools is also support evidence. Bundled stdio schemas alone do not establish server support; inspect the target capability. Do not claim an old server can close jobs.

| Tool | Bearer API | Arguments and response |
| --- | --- | --- |
| `get_account_usage` | `GET /account/usage` | `{}` → `{usage}` |
| `list_video_jobs` | `GET /video-jobs` | `{status?:"all"|"draft"|"active"|"history",limit?:1..50,cursor?:string}` → `{jobs,next_cursor,usage}`; defaults all/20; cursor is opaque |
| `cancel_video_job` | `POST /video-jobs/:id/cancel` | `{job_id}`; no body required → `{id,status:"cancelled",revision,job,usage}` |
| `close_video_job` | `POST /video-jobs/:id/close` | `{job_id,expected_revision:integer>=0}`; body `{expected_revision}` → `{id,status:"cancelled",revision,job,usage}` |

`usage` has `observed_at`, `active:{count,limit,remaining,counted_statuses,includes_unknown_statuses:true}`, `drafts:{count,limit,remaining,ttl_seconds}`, and `terminal_statuses`. Counts cover the whole account, not the current page or key. Active and draft limits default independently to 10; provider concurrency remains three and is a different limit. The capability also advertises `video_close: "/api/v1/video-jobs/:id/close"`; a bundled client schema alone does not establish live server support.

Each job summary has `id/title/status/stage/revision/created_at/updated_at/progress_updated_at/counts_toward_limit/quota_bucket/can_cancel/cancel_blocked_reason/can_close/close_blocked_reason/draft_expires_at/cancelled_at/cancellation_reason`. `counts_toward_limit` means active capacity; `quota_bucket` is `draft|active|null`. Use `progress_updated_at` for business progress. The server determines cancellation, closure and expiry safety; an unfamiliar status is conservatively active. The list is ordered by creation time then ID descending, and its cursor preserves account isolation.

Only user-selected or explicitly authorized disposable drafts may be cancelled. Never cancel the oldest task automatically. A repeated cancellation returns 200 with the original audit time. Foreign/missing IDs return 404; unsafe or non-draft jobs return 409 `video_job_not_cancellable` with `reason`, safe `message` and current `job`. Refresh and explain the conflict instead of forcing it. Cancelled prepare returns 409 `video_job_cancelled` and cannot queue the job.

Eligible never-started drafts expire at creation plus 86400 seconds as `cancelled`/`draft_expired`; reads never extend the deadline. User draft cancellation uses `user_cancelled`. A user who explicitly abandons one stopped review/attention job may close it when its current summary says `can_close:true`, supplying that summary's revision. Closing records `user_closed`, frees active capacity and keeps media and audit records; the original job cannot continue. A repeated close succeeds idempotently. Unsafe closure returns 409 `video_job_not_closable` with `reason`, safe `message`, and current `job`; revision conflicts may return `job_state_changed`. Refresh the same job and get a new decision. Never close tasks automatically or in bulk to bypass quota. Protected drafts have a blocked reason rather than an expiry promise. Cancellation/expiry retains input and audit records, deletes no media and does not clear unknown paid submissions or permits. Cancelling a draft frees only draft capacity.

Quota denial is 429 `video_draft_limit_reached` or `video_job_limit_reached` with `scope:"account"`, `quota_bucket`, `limit/count/remaining`, `retryable:false`, safe `message`, `usage` and `actions`. Draft actions are `list_video_jobs|cancel_video_job|continue_existing_job`; active actions are `list_video_jobs|continue_existing_job|close_video_job`. Show the actual counts and available actions. Do not loop POST, switch keys, auto-close tasks or invent Retry-After. Continue an existing eligible draft only if active admission succeeds; an active quota denial leaves the same draft available for later recovery.

The stdio bridge preserves approved lifecycle fields in JSON-RPC `error.data` (plus HTTP `status`) and a readable `error.message`; it drops arbitrary extra diagnostics and redacts configured credentials. Unknown transport/response outcomes use `api_request_outcome_unknown` with `retryable:false`, without automatically resubmitting. Remote MCP uses its server error envelope for the same public lifecycle fields. On 401, use native credential configuration and an authenticated read-only management check; public health is not proof of authentication. Never put credentials in chat, local project records or release archives.

Check live capability entries `video.delivery` and `video.templates`, each with `status: available`; packaged schemas do not prove deployment. These operations use the same account-scoped Bearer API. See [template workflow](../skills/video-generation/references/video-templates.md) for user choices and reuse rules.

| Tool | Bearer API | Arguments |
| --- | --- | --- |
| `get_video_delivery` | `GET /video-jobs/:id/delivery` | `{job_id}` |
| `submit_video_feedback` | `POST /video-jobs/:id/feedback` | `{job_id,decision,output_sha256,notes?,name?,category?,template_id?}`; job_id is path only |
| `list_video_templates` | `GET /video-templates` | `{status?:"active"|"archived"|"all",source_asset_id?,source_sha256?,limit?:1..50,cursor?}`; default active/20 |
| `get_video_template` | `GET /video-templates/:id` | `{template_id,version_id?}`; version_id is a query parameter |
| `update_video_template` | `PATCH /video-templates/:id` | `{template_id,name?,category?,archived?}`; at least one update, template_id is path only |

All IDs use 1–128 ASCII letters/digits/underscore/hyphen, hashes are 64 lowercase hexadecimal characters, and a supplied cursor is a nonempty base64url string ≤512 characters. Names ≤80 and categories ≤40 are single-line. Feedback names may be omitted or blank for a server default; update names must be nonempty. Notes ≤2000 may contain CR/LF/tab but no other C0 or DEL controls. Do not add unknown fields or normalize signed media URLs.

Delivery returns `{job_id,title,status,output_sha256,output,source,segments,feedback,can_feedback,template_save_supported}`. `output` is null or `{url,download_url,sha256,media}`; `source` has `{url,sha256,duration}`; each segment has `{index,accepted,url,download_url,sha256,media}` with nullable media/links/hash when unavailable. `media` contains duration/width/height and optional fps/frameCount. `feedback` is null or `{decision,notes,template_id,template_version_id}`. Never synthesize an official output from segment links. URLs can expire: read the same delivery again to refresh and use each URL byte-for-byte; do not add the API Bearer header to a media host.

Feedback decisions are `satisfied_save_template`, `satisfied`, `needs_changes`. Only an explicit user choice of the first saves a private template. Final feedback requires a completed output, current output hash, all candidates accepted and no lease, reflected by `can_feedback`; saving also requires `template_save_supported`. `template_id` is allowed only with `satisfied_save_template`, for an explicitly selected existing template's new version. Response is `{feedback,template,version_id}` with null template/version when none saved. Same-job/output saves are deduplicated server-side; a lost response still requires read-only reconciliation, not blind writes. A changed output or incomplete job may return 409; missing/foreign resources return 404.

Template lists return `{templates,next_cursor}`. Each summary has `id,code,name,category,archived,latest_version_id,version_count,source_asset_id,source_sha256,source_duration,thumbnail_url,source_url,preview_url,created_at,updated_at`; preview URLs may be null. `code` (for example T001) is for display; use `id` for calls. Source matching uses owned asset identity or known SHA256; newly uploaded identical bytes can match through their stored hash. Reads do not download/hash unknown legacy assets. Names are not unique and listing is paginated.

Detail returns `{template,versions,selected_version}`. Version summaries have `{id,version,created_at,source_job_id,output_sha256}`. `selected_version` has `{id,version,source_asset_id,source_sha256,output_sha256,workflow_profile:"sixref-v1",recipe_schema_version:1|2,create_payload,character_bindings}`; old schema1 responses can omit the character display list. The clean payload uses `segment_plan`, not job-state `segments`, and only contains creation fields. Schema2 resolves bound character slots to normal asset IDs plus fixed version/image indices in this public payload, while its stored recipe references the character version without copying images or descriptions. PATCH returns `{template}`. Versions are immutable; archives retain media and free no capacity. No hard-delete API exists.

`create_video_job` optionally takes `template_version_id` with a freshly reviewed clean six-reference payload. Template ownership, archive state, source identity/hash, workflow/audio strategy, time windows/durations/dependencies and ordered slot roles must match. Asset IDs, labels and creative text can be replaced. Changed structure needs a new independent plan and later a new satisfied template. Use the selected immutable version ID, never copy old consent, tokens, receipts, permits, candidate/accepted/tail state, attempts or history. Creation still uses normal quota, then new prepare, quote/budget authorization, paid render and candidate review. It never auto-prepares or renders.

Saving a video template likewise never creates a character. Read the [character workflow](../skills/character-library/references/character-workflow.md) before these operations.

## Character references in video creation

Both top-level and per-segment six-reference items accept `{asset_id,role,label,character_version_id?:string|null,image_index?:number}`. With a string version, role must be `character` and image_index an integer0–5; asset_id must equal the actual image pinned by that owned immutable version. The server verifies ownership, archive eligibility and image correspondence before atomic job creation. The bridge validates local shape and requires both six-reference and character-library capabilities before POST.

Explicit `character_version_id:null` is an authorized one-off replacement with role character and no image_index: no character is saved or pinned. Omitted version requires omitted index and preserves ordinary old references. Character binding fields in legacy/direct modes are rejected rather than dropped. For a schema2 template slot that was bound, the request must explicitly supply string or null; omission returns409 `character_binding_required`. Do not remove the template ID to evade it. New selection of an archived character is rejected; the identical fixed version already pinned by the explicitly selected action-template version may be reused unchanged. Character identity is replaceable without changing the action structural signature.

`selected_version.character_bindings` lists `{segment_index,reference_index,character_id,code,name,character_version_id,version,image_index}` with segment_index -1 for top-level refs. Delivery adds `character_references:[{asset_id,label,image_url,sha256,character_id?,character_version_id?,image_index?}]`, deduplicated by original asset ID. These are original inputs, not generated-video screenshots. The Expert can extract a selected frame from an existing downloaded video using available local tools, show it for selection and upload via existing supported tools; no server frame-extraction tool or paid generation is implied.

Descriptions remain immutable character metadata. Put relevant appearance requirements into the new visible plan within existing text limits; the worker must not secretly append mutable/latest character text. Keep original preparation snapshots, current quote/budget, candidate review, accepted predecessor tails and paid-state isolation. No fixed-version claim guarantees deterministic visual identity.
