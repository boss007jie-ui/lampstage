# Jobs and assets

Use `upload_local_asset` only in the bundled stdio bridge when the user provides an exact absolute local file path; it validates regular JPEG/PNG/WebP images up to 5 MiB and MP4/MOV/WebM videos up to 150 MiB, including file headers, before authenticated multipart upload. The remote HTTP MCP endpoint cannot access client files: use `upload_asset` there only for a public `http(s)` source URL. Keep the returned `asset_id`. Do not scan local directories, select files on the user's behalf or expose credentials.

For healthy queued/preparing/generating/assembling video tasks, call `get_job` after 30 seconds, backing off only to 60 seconds while unchanged. Bound each observation window to 45 minutes; an elapsed window is not a failed task or permission to resubmit. Handle review/attention/completed immediately. Actual rate limits and connection failures use the bounded exception policy in the [production guide](../video-generation/references/production-workflow.md), not blind polling. The guide also defines normal versus deep inspection and full-video-plus-segment delivery. If the host cannot continue an active wait, save the ID and explicitly report that observation stopped; do not claim an unscheduled background monitor exists.

Return a stable record containing `job_id`, `status`, `created_at`, `outputs`, `error_code` and `next_action`. Use `download_output` only for completed outputs and avoid logging tokens or signed URLs.

For image creation, first read the [image workflow](../image-generation/references/multi-reference-images.md). New image calls have explicit output count independent of reference count, and creation starts paid work. Save the returned ID and use `get_job` for that image task. An unknown create result without an ID cannot be reconciled by `list_video_jobs`: use an actually available account image-history interface, or report unresolved status and stop automatic resubmission. There is no `list_image_jobs` tool in this package. Image reference metadata describes the selected inputs, not successful visual identity preservation.

Use signed media URLs verbatim, including all encoding and query parameters. Change only the local destination filename, never `response-content-disposition`, signature or URL path. On 403/expiry, use `get_video_delivery` or `get_job` for fresh source/candidate/final links, or `download_output` for completed output, and retry the download once unchanged; a further failure remains a download problem. Do not attach API Bearer credentials to media domains or regenerate video. Durable records contain IDs, hashes and local paths, not signed URLs. Deliver both the full-video entry and every ordered segment entry. If official assembly fails, identify any authorized local fallback separately and explicitly state that no official output exists.

Discover delivery/template support through the live remote tools and `video.delivery` / `video.templates` capabilities. Read the [template guide](../video-generation/references/video-templates.md) before using `submit_video_feedback`, template list/detail/update or `create_video_job.template_version_id`; a bundled tool list alone is not server support. `get_video_delivery` is read-only and does not create, render, accept or save anything.

For character records, check live `characters.library` and read [character-library](../character-library/SKILL.md). `list_character_assets` lists owned original images without hashing writes; prefer known existing asset IDs over uploading again. Existing upload tools receive server-side exact-byte deduplication when supported, while product asset rows may remain distinct. Do not claim all originals are private or historical duplicates were deleted. `save_character` uses a stable client key for the explicitly selected images; ambiguous results require list/detail inspection before retry with the same request/key. It creates neither a video job nor satisfaction feedback/template. Original `character_references` in delivery are not generated output frames.

Before job creation, keep the project plan and checks in the local task workspace, outside the Expert installation. Explicit submission creates one video task. Save its returned ID, plan/asset IDs, status and revision immediately, and use that ID for all later operations. Store no API keys, authorization headers or signed media URLs in the record. If saving is unavailable, return the ID and state the limitation. Do not create diagnostic jobs or claim a remote draft-edit or create-idempotency endpoint exists.

Discover lifecycle support from the `video.replicate` capability entry: `lifecycle.version: 1`, `draft_limit: 10`, `active_limit: 10`, `draft_ttl_seconds: 86400`, `cancellation: "never_started_drafts"`, and terminal statuses `completed`, `failed`, `cancelled`. For closure also require `lifecycle.closing: "explicitly_abandoned_stopped_review_or_attention"` or the live remote server's `close_video_job` tool. The bundled stdio bridge advertises client tools even for older servers, so check its target server's capability before promising these functions. If unsupported, keep the known-ID workflow and clearly report the missing management capability; do not invent cancellation or retry creation to probe support.

- `get_account_usage {}` returns `{usage}`. `active` and `drafts` each have count/limit/remaining; active additionally names counted statuses and conservatively includes unknown statuses. Counts cover the account, not one page or one API key.
- `list_video_jobs {status?,limit?,cursor?}` accepts `all|draft|active|history`, limit 1–50, and the opaque `next_cursor` from the preceding response. It returns `{jobs,next_cursor,usage}`. Use server-provided `quota_bucket`, `can_cancel`, `cancel_blocked_reason`, `can_close`, `close_blocked_reason` and `draft_expires_at`; do not infer eligibility from `status` alone. `counts_toward_limit` refers only to active capacity. Show `progress_updated_at` for business progress, not heartbeat-driven `updated_at`.
- `cancel_video_job {job_id}` applies only to a task the user selected or explicitly authorized as disposable. Do not automatically choose the oldest, bulk-cancel unrelated work or force an unsafe cancellation. The server rechecks eligibility and returns the cancelled job plus usage. Repeat cancellation is server-idempotent; this does not imply create idempotency. On 409, refresh that task/list and explain the blocked reason; never try another task automatically.
- `close_video_job {job_id,expected_revision}` closes only a specific stopped review/attention job that the user explicitly abandons and whose latest summary says `can_close:true`. Use that summary's integer revision. The server rechecks safety and returns `{id,status:"cancelled",revision,job,usage}`; repeated closure is idempotent. Never automatically close the oldest job or batch-close tasks as a quota workaround. A 409 `video_job_not_closable` includes `reason`, safe `message` and current `job`; `job_state_changed` means refresh the same job and obtain a new decision rather than forcing it.

On `429 video_draft_limit_reached` or `429 video_job_limit_reached`, preserve the exact code, safe message, usage, actions and `retryable:false`. Read usage/list; do not loop POST, suggest changing keys or invent a Retry-After. For full draft capacity, the user may continue an existing draft if active capacity allows, or select an eligible draft to cancel. For full active capacity, continue existing work as its state allows; if the user chooses to abandon a specific stopped review/attention task and its summary says `can_close:true`, close it with its revision. Cancelling a draft will not release an active slot. These are simultaneous limits, not daily production totals or storage byte limits.

A lost video-create response does not prove the task was rejected. Do not automatically submit again. List recent video tasks and query candidate IDs to establish the actual result; title alone is insufficient. If the evidence is ambiguous or a task has not yet appeared, explain the uncertainty and stop further creation. When the ID is known, poll that ID with backoff. For recorded unknown paid video submissions, use the existing reconciliation workflow; do not cancel or regenerate as a shortcut. The image-specific recovery rule above applies to image creation.

Eligible never-started drafts expire at creation plus 86400 seconds, becoming `cancelled` with `cancellation_reason: "draft_expired"`. Reads do not extend that deadline. Draft cancellation records `user_cancelled`; explicit stopped-job closure records `user_closed`. Protected drafts, ongoing work, receipt/permit evidence and unknown outcomes must not be treated as disposable. The service retains input/audit records and does not delete media. Cancelled or closed jobs cannot be resumed or prepared again.

On 401, use WorkBuddy's supported native credential configuration outside chat, then an authenticated read-only management request when available. Public health/capabilities do not validate a key. Never ask for credentials in chat, print them, create a test job, or modify host configuration silently.
